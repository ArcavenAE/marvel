# finding-marvel-lt30: marvel's service record covers running a service, not installing, configuring, upgrading or persisting one

**Date:** 2026-11-11
**Confidence:** frontier. A gap analysis against the merged design record, with one host's reboot as the evidence.
**Probe:** none; observed while restoring kinu after an OS upgrade.
**Placement:** marvel. The subject is what marvel does across a service's life on a host. bd, NATS and the other providers named here are objects.

## Why this matters

The operator's intent, word for word (2026-11-11): marvel "needs to be able to setup and manage the users' chosen services like bd and nats (or other ticketing services and other message busses, backends, routers, credential vaults, etc) which means install, configure, upgrade, monitor, manage".

Today marvel's design covers the middle of that list, for one class. A user who wants bd and NATS running gets them there by hand, and on kinu the hand-made path failed silently at the first reboot.

## The evidence: kinu, 2026-11-11

kinu runs its two NATS servers, its dolt server and the marvel daemon as launchd user agents, installed from the orchestrator (`tools/install-kinu-launch-agents.sh`, `ops/launchd/`), outside marvel. After an OS upgrade and reboot:

- Both NATS agents exited with status 1 on every start, 939 times each, because each server's config reads a variable (`DIRECTOR_PHASE0_STORE`, `HUB_LEAF_ADVERTISE`) that only its launcher script exports, and the plists run `nats-server` directly.
- The installer's dry run reported both as "loaded, plist current: nothing to do". It checks that a job is loaded, not that it runs.
- The global hub's launcher and config exist only on the host, generated by an operator step, and are in no repository.
- The marvel daemon came up under launchd with the bare launchd PATH (`/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin`), which every seat it spawns inherits, so a seat would not find `claude`, `codex` or the mise tools.

Each of these is a stage marvel's record does not cover: first configuration (the launcher environment), persistence across a reboot, a health reading that includes "is it running", and the environment marvel itself starts with.

## What the record covers

| Stage | Covered today | Where |
|---|---|---|
| Declare | yes: class, provider, mode, caller identity | `services-list.md`, `internal/service` |
| Run (start, stop, restart, reload) | bus only, mode `managed` | `bus-as-service.md`, MS-6, MS-8 (the extraction gate before a second provider) |
| Monitor (health, status) | bus only; adopted entries get a read-only probe | `bus-as-service.md` section 3, MS-7a |
| Install (put the binary on the host) | no | none |
| First configure (config, store, users, launch environment on a new host) | bus only: marvel renders the managed broker's config and users | `bus-as-service.md`; nothing for any other provider |
| Upgrade (a new provider version) | a vision line only | `bus-as-service.md` "Upgrade"; orc idea `marvel-staged-activation-upgrades.md` |
| Persist across a reboot (marvel's own daemon, and so everything it supervises) | no; the admin guide says "or with systemd, launchd, etc." | `docs/admin-guide.md`, "Background daemon" |
| bd as a provider | open question | `question-bd-managed-extended-service` |
| Breadth (task, kv, file, secret classes) | ideas | `_kos/ideas/services-catalog.md`, `marvel-service-classes-beyond-the-bus.md` |

## Constraints the gap must be closed inside

These are already ratified, so any design for the missing stages starts from them:

- **Independence (SOUL section 2, ADR-005).** bd and NATS must keep working without marvel, and marvel must work without them. Managing a service is an offer, never a precondition.
- **User sovereignty (SOUL section 1).** The user chooses the provider. marvel's job is to install and manage the one chosen, not to pick it.
- **MS-7.** Nothing in mode `adopted` or `external` gets a lifecycle verb, upgrades included. Install and upgrade are verbs of mode `managed` only.
- **Custody (ADR-009).** A credential vault is a service marvel may broker and never hold the long-lived grant of; the install and configure stages for a vault inherit that line.
- **Automation boundary (ADR-007).** An upgrade marvel proposes is confirm-or-override; a health reading informs and never gates.

## Open questions (not answered here)

1. Install: does marvel install a provider (a package manager call, a pinned download with a checksum), or only check for it and say what is missing?
2. Persistence: should marvel install its own login or boot unit (launchd, systemd), and with what environment, since that environment is the one every seat inherits?
3. First configure: where does a host-local value that is not a secret (an advertise address, a store path) live so that a fresh host gets it without an operator step, and where does one that is a secret live under ADR-009?
4. Upgrade: is a provider upgrade a Shift (the vision line), a staged activation, or its own verb, and what is the rollback?
5. Health: should a managed service's reading say "not running, last exit N, restarted M times" as a first-class state, which is what kinu's installer could not say?
6. Does bd (dolt server) become the second managed provider, the case MS-8's extraction gate is waiting for?

No tickets. This finding records the gap and the evidence so a design can start from them.
