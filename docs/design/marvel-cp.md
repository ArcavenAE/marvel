# marvel cp: a contained, verified file copy between marvel daemons

**Status:** design for review, 2026-11-01; R1 to R4 ruled by the operator 2026-11-01 (section 9). Nothing here is built, and nothing here is on by default.
**Starts from:** `_kos/ideas/marvel-scp-verified-transfer.md` (2026-09-21) and the draft brief `_kos/probes/brief-cross-host-artifact-transfer.md` (2026-10-24). Neither scoped containment on the receiving side; this design does.
**Read at:** marvel `origin/main` a19ec4b5; revision 2 re-read at 52af1756 and against the Go 1.26.5 `os` source; revision 4 re-checked at 182fadf0 (2026-11-17) and against the Go 1.27.0 `os` source.
**Revision 2 (2026-11-01).** A review measured three overstatements in revision 1, and they are fixed here: `Root.OpenFile` follows a link inside the jail even with `O_NOFOLLOW` (C6, C8); `os.Root` contains names, not inodes, so a hard link could reach outside content (C10); and the 32 MiB bound the size cap cited is the client's reply bound, while the daemon reads a request with no bound (I3, I5). It also takes two lows: temporary files move to a reserved directory (O1, C11), and the policy file's ancestors and the read itself are checked (A1).

**Why.** marvel already carries an authenticated channel between hosts (`mrvl://`), and the one recorded transfer failure (section 1) happened between two hosts that channel joined. A file copy over it is useful only if it cannot be turned into a way to write anywhere on the receiving host, so this design puts containment, no-clobber writes and an owner-held off switch ahead of the verb.

**Revision 3 (2026-11-01).** The operator asked whether only marvel or sideshow should manage the files transferred or stored for casts, as reference copies rather than working copies. Section 2a answers that: cp writes no reference copy and no seat's working directory, only the owner's jail, and the jail is refused if it overlaps any store a cast is read from. It uses the terms of marvel `docs/design/companies.md` and sideshow `docs/marvel-company-target.md` (both in review) without renaming anything. Two text lows from the second review are folded in (C10, I5). Revision 3a aligns section 2a with the companies design's third revision: marvel writes the builtin company and nothing else in its own root, enforcement is named E0, E1 and E2 as that design names it, and C12 also refuses the per-session working-copy directories.

**Revision 4 (2026-11-17).** Re-checked at marvel 182fadf0 for the build (aae-orc-wrzec, marvel#1238) after a five-seat design party, whose votes and recorded dissent are kept outside this repository. The request bound this design waited on is built (#1350, closing #1197), so I5 and I6 now describe it. The refusal set (C12) no longer reads a `companies.roots` key that does not exist yet, and it now refuses marvel's own home. The audit line (U1) gets a home, since the daemon had no audit log. Containment details that the party measured are fixed: the reserved directory is verified before use (C13), every refused root is compared by file identity (C12), the parent directory is synced after placing a file (O1), a `flock` serializes placement (O4), and the policy decode is strict (A1). Section 12 is the build plan. One question goes to the operator (R5).

## 1. Use cases

I searched the fleet's records for every case where a file was needed on a host other than the one holding it: marvel's `_kos`, the orchestrator's `_kos`, the director simulation's notes and requirements, and the orchestrator's rules. The incident that earned the idea was the positive control, and it was found. Ten cases turned up. Grouped by what serves them today:

| # | case (date) | what had to move | served today by | cp only? |
|---|---|---|---|---|
| 1 | the ops manifest (2026-09-21) | a ~15 KB manifest held in one seat's scratch on host A, needed to run `marvel work` against host B | remote `marvel --cluster B work <file>`: the client sends the manifest bytes in the `apply` RPC (`cmd/marvel/main.go`, `manifest_data`), so the file never needs to be on B. The record shows the binding constraint was that the seat's harness refused to run `marvel work` at all, and the copy was a workaround for that | no |
| 2 | two skills for a seat on another cluster (about 2026-09-25) | skill directories | git: they were already published in a repository the other side could read | no |
| 3 | a review written on one cluster, needed by seats on another (2026-09-26) | a review document | git, if the review may live in a repository; otherwise it was re-sent as message text, in parts, and a count was misstated on the way | only for an artifact that may not enter a repository |
| 4 | private data, between two clusters (2026-09-30) | private data | nothing. SSH was refused both ways; git is wrong for private data; the record says the bus is the wrong carrier for it. It went to the operator, unsolved | **yes** |
| 5 | design notes in a git-ignored session directory, during a cross-cluster work migration (finding-220) | session notes | partly: code went on a pushed branch, and the answers the successor needed were written into tracker notes both clusters read | only for notes kept out of git on purpose |
| 6 | the operator's global agent instructions, to two more hosts (2026-10-05) | one config file | git and an installer. The operator ruled out the copy: "we do not scp files around" | no, by the operator's word |
| 7 | a rule added to per-host seat manifests on one host, needed on two more (2026-10-10) | untracked manifest files | nothing today; the operator's objection was to "so many bits and parts strewn around in many places", which argues for tracked manifests, not copies | no |
| 8 to 10 | a bus seed, a provider key script, seats kept on the host that holds their credentials | credentials | `marvel credential put --cluster` for the first; the credential plane for the rest | no, by ADR-009 |

**The answer.** One recorded case, 4, is served by nothing but a file copy. Two more, 3 and 5, need one only for an artifact that is deliberately kept out of every repository. The rest are served by remote `marvel work`, by git, or by the credential plane, and in two of them (6 and 7) the operator's stated preference is fewer copies of files on hosts, not an easier way to make them.

That makes the use case narrow and sensitive. The one case nothing serves is private data. This design is therefore written for that case: a jail the owner names, off unless the owner turns it on, and no way for marvel to widen its own reach. If the operator rules that case 4 has another carrier, nothing is left for `marvel cp` to serve and it should not be built (section 9, R1).

## 2. Shape

- `marvel cp <src> <cluster>:<dst>` pushes a local file to a remote daemon. `marvel cp <cluster>:<src> <dst>` pulls one. `--workspace <ws>` names the jail (section 3); it defaults to the client's workspace.
- Two daemon methods, `file.put` and `file.get`, over the same RPC as every other method. The client reads and writes its own side; the daemon touches only its jail.
- One regular file per call. No directories, no recursion, no streaming. A tree is a tarball the caller makes, or a git push.
- `--replace` is the only flag that changes what a write may do (section 4).

## 2a. Reference copies, working copies, and where cp writes

**The tiers, as the companies design and the sideshow target define them:**
- **Master.** The source a library is edited in, outside marvel: for roles, the role library's git repository, under its owner's review. It stays the source. Neither marvel nor sideshow writes it, and cp never reads or writes it.
- **Reference copies.** Each installed company version, `<root>/<name>/<version>/`, is immutable. An installer writes it: sideshow into its own store (`$SIDESHOW_HOME/packs/<name>/<version>/`, with `SIDESHOW_HOME` defaulting to `$HOME/.local/share/sideshow`), or any tool that produces a valid version directory from the master (a release tarball, `git archive`). marvel owns one root, `~/.local/share/marvel/companies`, and writes only the builtin company there, materialized from its own binary; it writes no other reference copy. That is the companies design's rule, and this design keeps it.
- **Working copies.** A session's working copy lives under `~/.marvel/run/sessions/<s>/company/`, with an `origin.json` naming the reference copy it came from, as the companies design specifies. It is never a root and is never promoted into one. marvel still renders the prompt from the pinned version at launch and stamps its hash on the session (`marvel.prompt_artifact.sha256`).

**Who writes a reference copy, and how that is enforced.** The owning writer is the installer, in its own store, and marvel for the builtin only; marvel records the tree hash the first time it resolves `name@version` and refuses any later resolve whose hash differs. The companies design names three enforcement tiers, and this design uses them unchanged rather than adding its own:
- **E0.** Modes plus hash: detection only, since the owner of a file can restore its bits.
- **E1.** marvel starts every session under a write-deny profile covering all company roots and other sessions' working copies.
- **E2.** An opt-in dedicated store owner, reached by `sudo -u`, so no seat's user can write the store at all.
Which tier a host runs, and whether any is on by default, belong to the companies design and its rulings, not to cp: companies.md calls 2 and 3, and call 3 of the sideshow target doc (`docs/marvel-company-target.md`). cp needs no tier of its own: its writes are made by the daemon, not by a session, so E1 does not cover them, and C12 below is what keeps the daemon's cp writes out of every root and working copy whatever tier is in force.

**Where cp writes: neither a reference store nor a seat's working area.**
- **C12.** cp writes only into the owner's jail (section 3). cp refuses a jail that is, holds, or sits inside any of these, compared by file identity (`os.SameFile` over the jail's ancestors for "inside or equal", and over each refused root's ancestors for "holds"), never by string: marvel's own home (`Layout.Home`, which holds `authorized_keys`, the host key and the client keys); marvel's company store (`~/.local/share/marvel/companies`); the sessions directory and every session's working copy (`~/.marvel/run/sessions/<s>/company/`); any seat's `workdir`; every path in `companies.roots` once the companies build adds that key (it does not exist at 182fadf0, and the companies design says nothing of it is built); and every root the owner's policy lists for that workspace (A3), which can add refusals and never remove one. A listed root that does not exist refuses both methods for that workspace, since it could be created inside the jail after the check. cp reads no sideshow setting of its own (ADR-005): sideshow's store is refused once it is registered in `companies.roots` or listed by the owner. A refused jail turns both methods off for that workspace, and the refusal names the class that matched ("C12: jail holds a session working copy"), never the absolute path. The check runs on the resolved paths at each call, after A1's policy read. So cp can never create, change or replace a reference copy, never write into a session's working copy or a seat's working tree, and never reach marvel's own keys. The companies design makes the same refusal from its side: a company root that is, or holds, a cp jail is refused.
- **No promotion.** A file that arrives by cp is neither a reference copy nor a working copy of a cast. Nothing in marvel or sideshow reads the jail as a root, and no cp verb moves a file out of it. A file that should become part of a library goes into the master, by its owner's review, and reaches hosts the way every version does: through an installer, as a new reference copy with its own hash.
- **A copy derived from a reference copy.** When a cp source is a file inside a reference copy, the client records `derived_from = "<name>@<version>:<relative path>"` with that file's sha256 in the audit line (U1), so the copy is traceable to the exact reference it came from. It is still a jail file, not a reference copy.

**How this fits R1 to R4.** Section 1's one case served only by cp is private data, which is not cast material. Distributing a cast is already served by the master and the installers, so it is not a use case for cp, and this section adds no case to section 1. R1 to R4 are unchanged in substance; R2 now also reads "off until the request-bound change merges" (I5). There is no R5: which enforcement tier a host runs is ruled under the companies design.

## 3. Containment on the receiving side

**The jail.** Each workspace that the owner enables has one jail directory on each daemon host, named in the owner's policy (section 6). Every `dst` and `src` is a path relative to that jail. There is no default jail: a workspace the policy does not name has none, and both methods refuse it.

**Path rules, checked on the string before any file system call:**
- C1. Relative only: a leading `/`, a drive or volume form, or an empty path is refused.
- C2. No `..` component, no `.` component, no empty component (`a//b`), no NUL, no component over 255 bytes, no path over 1024 bytes.
- C3. Each component is printable UTF-8 with no control characters. A leading `-` is allowed (it is never passed to a shell).

**Resolution, with no gap between the check and the use:**
- C4. The daemon opens the jail once per call with `os.OpenRoot` and does every later operation (stat, open, create, link, rename, remove) through that root. `os.Root` resolves each path relative to the opened directory and refuses any resolution that would leave it, including through a symlink and including a link that appears after an earlier check, because it walks the path with the opened directory's descriptor rather than re-resolving a string. It does follow a link whose target stays inside the jail, so containment and "no links" are separate properties; C6 adds the second. This is the property that closes the time-of-check, time-of-use gap; a resolve-then-compare-the-prefix check on a string does not. Two limits, stated so nobody relies on more: `os.Root` needs Go 1.25 for `Link` and `Rename` (marvel's `go.mod` is 1.26), and it does not detect a mount point inside the jail, which only the owner can create there.
- C5. The jail root itself is checked once, when the call opens it: it must be a directory, not a link (`Lstat`), and `filepath.EvalSymlinks` of its configured path must equal the path, so the owner's configured location is the real one. This repeats the handoff write's directory check (`internal/team/handoff_put.go:305-325`). Because the default macOS volume ignores case, equality alone is not identity; C12's comparisons use `os.SameFile`, never strings.
- C6. Links inside the jail are refused. `O_NOFOLLOW` alone does not do this: `Root.OpenFile` adds `O_NOFOLLOW`, and on the resulting error it reads the link and follows it within the root, except when the flags are `O_CREATE|O_EXCL` (Go 1.26.5 `src/os/root_unix.go`, `rootOpenFileNolog` and `checkSymlink`). So:
  - **Parents.** Before any open, the daemon `Lstat`s each parent component through the root and refuses a link anywhere on the path.
  - **The final name, on a read or a replace.** It `Lstat`s the name through the root and requires a regular file, opens it, `fstat`s the open file, and refuses unless `os.SameFile` holds between the two. A link or a different file swapped in between the `Lstat` and the open is caught by that comparison, so the bytes served are always those of the file the `Lstat` saw.
  - **The final name, on a create.** The temporary file is created with `O_CREATE|O_EXCL`, which never follows a link.
  - A link swapped into a parent after the walk can still only point inside the jail (C4), so containment holds; the walk and the identity check exist so a link that stays inside is refused too, and the audit records the refusal.
- C7. Parents must exist. `file.put` creates no directories. A missing parent is refused with its name.

**What may be written or read:**
- C8. Regular files only. `file.put` writes a new regular file with mode `0600`, never with set-id, sticky or execute bits, whatever the source's mode. `file.get` follows C6's sequence (`Lstat` regular, open with `O_NONBLOCK`, `fstat`, `os.SameFile`), so a FIFO, socket or device is never read and a link is never followed.
- C10. One name per file, at `fstat` time. `os.Root` contains names, not inodes: a hard link inside the jail to a file outside it passes every name check and reads the outside content. So `file.get`, and the read of a replaced target for its audit digest (O2), refuse a file whose `fstat` link count is over 1. This is a property of the inode when it is opened, not of its history: a hard link made into the jail and then stripped of its outside name has a link count of 1 and passes; making it needs write access outside the jail, so it is a visible act. A file `file.put` creates has a link count of 1 once its temporary name is gone (O1). Between `Root.Link` and the removal of the temporary name the new file has a link count of 2, so a `file.get` of it in that window, or after a crash inside that window, is refused until the temporary name is gone: removed by the put, or by the sweep in O1 once it is over an hour old. That is safe: the get fails closed and can be retried, and nothing outside the jail is reachable through it.
- C9. A target that exists and is not a regular file is refused, with `--replace` or without.
- C11. The name `.marvel-cp-tmp` is reserved: a path whose first component is that name is refused by both methods, so no call can read or write a temporary file (O1).
- C13. The reserved directory is verified before every use: it is opened through the root, `fstat`ed, and must be `os.SameFile` with an `Lstat` of the same name, a directory owned by the daemon's uid with mode `0700`. Otherwise both methods refuse. `os.Root` follows a link in a parent component when the target stays inside the jail, so without this a link in place of `.marvel-cp-tmp` would point the sweep (O1) at the owner's files.

**What the jail is not.** Every seat on a host runs as the daemon's user (no seat launch switches uid), so every seat on the receiving host can read the jail directly, bypassing cp, the policy and the audit. The jail contains cp; it is not a confidentiality boundary against local seats. The later boundary is an E1 read-deny on every jail; whether case 4 may be served before it exists is R5. And every file cp lands is untrusted data to every reader, the same as material collected from a third party: a harness or a seat that reads the jail reads text a remote caller chose.

## 4. Overwrite

- O1. **No clobber by default.** The daemon writes a temporary file in the jail's reserved directory, `.marvel-cp-tmp/<random>` (mode `0700` directory, verified by C13; file created with `O_CREATE|O_EXCL`, through the root), syncs it, checks the digest (section 5), then, under the O4 lock, writes and syncs the audit intent line (U1), links it to the target name with `Root.Link`, syncs the parent directory, and writes the outcome line. A link fails if the name exists, so "refuse an existing target" and "place the file" are one atomic step, and two concurrent puts to one name cannot both land. The temporary name is removed afterwards. A refusal removes it. The parent-directory sync makes the new name durable before the audit calls it `written`; on darwin `Sync` is `F_FULLFSYNC`, which falls back to plain `fsync` on a file system that does not support it (a network mount), with weaker durability and no warning (`internal/poll/fd_fsync_darwin.go`).
  - The reserved directory is inside the jail, so it is on the jail's file system and `Link` and `Rename` from it stay atomic. No call can name it (C11), so a half-written file is never readable through cp.
  - A crash can leave a temporary file behind. Each call first removes, through the verified reserved directory (C13), any regular file in it older than one hour, so leftovers do not accumulate. The hour also keeps one daemon from removing another daemon's live temporary file when two share a jail.
  - A crash or a reexec after `Root.Link` and before the outcome line leaves the target in place (C10) with an intent line and no outcome line, which the audit reads as "may have landed" (a reexec does not wait for a request handler: `internal/daemon/daemon.go:1058`). A retried put meets the target and is refused, as for any existing target, including one with identical bytes: a put that confirmed equal content would let a put-only caller test whether the jail holds bytes it guessed. The client recovers with a `file.get` where the policy allows one, or by sending again with `--replace`. The daemon never replaces on its own.
- O2. **`--replace`** writes and checks the temporary file the same way and, under the O4 lock, confirms the target is absent or a regular file with one link (C9, C10), reads its size and sha256 through the root, writes the intent line, renames the temporary file over it with `Root.Rename`, syncs the parent directory, and writes the outcome line. A reader sees the old file or the new one, never a partial one. The audit line records the replaced file's size and sha256.
- O3. The pull side follows the same rules on the client: no clobber unless `--replace`, temporary file then link or rename, in the destination's directory.
- O4. **One placement at a time per jail.** The check, the intent line, the link or rename, the parent sync and the outcome line run under a `flock` on the reserved directory's verified descriptor (C13), never during the temporary write or the hash. A lock on a descriptor, not a mutex, so it holds across two daemons that share a jail, and the kernel releases it when the holder exits; Go opens files close-on-exec, so a reexec releases it too (an assumption from Go's default and the kernel's `flock` semantics, not a measured property). Without it, two concurrent replaces both record the first predecessor and the second replacement's predecessor is lost.

## 5. Integrity and size

- I1. The sender computes the sha256 of the bytes it sends and sends it with them. The receiver hashes while writing and refuses a mismatch before O1's link or O2's rename. The receiver returns its own digest, and the client compares it too, so the check holds end to end and not only at one hop. It is a transit check, not a placement guarantee: between the hash and the link, any process running as the daemon's user can reopen the temporary file by name and change its bytes, and on a single-user host that is every seat.
- I2. `file.get` returns the digest of the bytes it read from the opened file, and the client checks it before placing the file (O3).
- I3. Size: no cp-specific cap (operator ruling R4, option 3). The existing transport limits set the ceiling, and a file over the limit fails at the transport.
  - **On `file.put`** the request bound in I5 (24 MiB) is the ceiling. With base64 and the envelope, the largest file that fits is about 18 MiB; the bound counts bytes read, including the decoder's read-ahead, so the exact ceiling is approximate and a request that fills the bound exactly can be refused. The daemon still stops and cleans up if the bytes exceed the declared size.
  - **On `file.get`** the client's 32 MiB reply bound (`maxReplyBytes`, `internal/daemonrpc/exchange.go:39-41`) is the ceiling, so the largest file that fits is just under 24 MiB in base64. The daemon enforces that limit before it reads a byte: it refuses a `file.get` whose opened file's `fstat` size, base64-encoded with the reply envelope, could not fit under 32 MiB. That adds no cp-specific cap (ruled by director 2026-11-02 as matching option 3; the operator may override). The client's own reply bound stays as a second check.
  - Larger files are out of scope.
- I5. **A request bound on the daemon, built.** marvel#1197 is closed by #1350: a bounded reader sits under the request decode for every method, before the method is known, and past 24 MiB the daemon answers `request too large: over <bound>` (`internal/daemon/daemon.go:1174`, `internal/daemon/request_bound.go`). The client refuses a request whose encoding passes the bound before it dials (`internal/daemonrpc/client.go:113`). The largest request measured is about 0.38 MiB (`internal/daemonrpc/request_bound.go`), the measurement this item asked for. The bound is a variable tests lower, so the build adds a guard that refuses both methods when it is 0 or less (ruled with the landing order, card r2-landing-order).
- I6. At most two `file.put` or `file.get` calls run at once per daemon; a third is refused as busy. The cap is counted after the decode, so it bounds disk and hashing work, not decode memory: every method has had the same decode exposure since the bound landed, and each put holds its body about three times while decoding (the decoder buffer, the raw `Params`, the decoded bytes), so the memory a burst of puts can hold is bounded by the request bound and the connection count, not by this cap. Two daemons that share a jail run four calls at once.
- I4. An optional per-workspace daily byte budget in the policy; past it, both methods refuse until the next UTC day. The counter is in memory and per daemon: a reexec resets it, and the first budgeted call after a daemon start writes one daemon-log line saying the counters start at zero. It is not rebuilt from the audit file, which any seat can rewrite and which rotates.

## 6. Authorization and the owner's off switch

**The owner's policy is a ceiling marvel cannot write.** It follows the stance in `_kos/ideas/mrvl-proxy-nats-and-generic-relays.md`: the control over a channel that can write files onto a host sits outside marvel.
- A1. The policy is a TOML file at a fixed path. Where that path is (and whether it is per host or per daemon home) is open with the operator (card wrzec-1); the build injects it in tests and names it as an open item until the owner rules. The daemon reads the policy on every `file.put` and `file.get` call, before anything else, so no reload step exists to forget. The read and the checks use one file descriptor: open with `O_NOFOLLOW`, `fstat` that descriptor for owner and mode, and parse from the same descriptor, so the file checked is the file read. The decode is strict: an unknown key anywhere refuses the call and names the key, and a policy without `enabled = true` is off. The file must be owned by a user other than the daemon's and not writable by the daemon's user, and so must every directory from its parent up to `/`. The walk runs over the resolved path (on macOS `/etc`, `/var` and `/tmp` are links into `/private`) and asks the kernel whether the daemon can write each one (`faccessat` with `W_OK`, which counts every group the daemon is in and any ACL), not the mode bits. If any check fails, or the file is absent or unreadable, the call is refused and the refusal names which check. On a single-user host this means the owner installs it with elevated rights, which is the point: marvel cannot turn its own file channel on.
- A2. Absent policy means off. There is no built-in default that enables either method.
- A3. The policy names, per workspace: the jail path; which directions are allowed (`put`, `get`, both, neither); the callers allowed per direction, by `mrvl://` key fingerprint and by the literal `local` for the daemon's own socket; optional path prefixes within the jail per caller and direction; extra refused roots (C12), which can only add refusals; the daily budget. It names no size cap (ruling R4) and nothing that changes the K1 list.
- A4. marvel's own authorization can only narrow the policy. A key needs the `admin` scope, or a new `file` scope that may call `file.put` and `file.get` and nothing else, and it must also be allowed by the policy. A caller the policy allows but whose key scope does not is refused, and so is the reverse. `credential-push` keys may never call either method.
- A5. Local callers are not trusted by being local. Every seat on a host holds the local socket (`localCaller`, `internal/daemon/scope.go:108`, and the note at `:119`), so `local` is a caller the policy must name like any other, and the design has no way to tell one local seat from another until the principal model lands (aae-orc-bs3x). Until then the recommended policy names `local` for nothing. A remote fingerprint has the same limit: it names a key, and every seat on the calling host runs as the user who can use that host's keys, so A7 narrows which key a call uses.
- A6. Turning it off: removing the policy file, or setting `enabled = false` in it, takes effect on the next call, with no restart. A call already past its policy read finishes or fails on its own. A `file` key has two revocation paths: marvel removes its line from `authorized_keys` (marvel's own act, which marvel can undo), or the owner removes its fingerprint from the policy (the control marvel cannot undo, effective on the next call). When a call's policy result differs from the previous call's (on to off, or a check starting or stopping failing), the daemon writes one line to its log naming the rule, never the policy's contents; the previous result is held in memory, so the first call after a start always writes one.
- A7. **The client names its key.** For `file.put` and `file.get` the client refuses the implicit identity chain (the default client key, `SSH_AUTH_SOCK`, `~/.ssh/id_*`, `internal/daemonrpc/client.go:578-632`) and needs an explicit identity, so a call cannot ride on whatever key the caller's shell happens to hold, including a key that is authority at a third party. This narrows the path; it does not separate seats on one host. The client sets a timeout on the exchange (the default is none, `client.go:75-79`) and reads a timeout as unknown, not as a refusal.
- A8. **The case-4 gate (pending R5).** This item is the one place the R5 ruling lands. Drafted on the assumption of R5 option (2), as the supervisor directed while the operator rules: both methods refuse, with rule `A8`, on any daemon whose sessions do not run under an E1 profile that denies reads of every cp jail. E1 is not built, so today both methods refuse on every daemon, and cp is built and tested but not usable for case 4. If the operator rules (1) or (3), this item is removed and nothing else changes.

## 7. Audit

- U1. Every call, allowed or refused, writes JSON lines to a cp audit file under the daemon's log directory, through marvel's size-rotating writer (`internal/rlog`, mode `0600`, `O_APPEND`), and emits a `file.put` or `file.get` event. A placement writes an intent line before the link or rename and an outcome line after (O1, O2). A line carries: time, the daemon (a hash of its home and its start time), caller (key fingerprint or `local`), key scope, direction, workspace, relative path, declared and actual size, sha256 of the bytes, outcome (`intent`, `written`, `replaced`, `read`, or `refused` with the rule that refused it), and for a replace the old file's size and sha256. A K1 refusal records the name and the rule and no digest, since a digest of a refused credential file is a fingerprint of a secret. The event carries the path's sha256 and length, not the path, because events reach every watcher and can leave the host. The audit fails closed: a call whose line cannot be written is refused before anything enters the jail. The file is a record, not a control: any seat runs as the daemon's user and can rewrite it, and rotation drops the oldest lines once the cap is reached.
- U2. Never the file's content, never a credential, and never the absolute jail path in an event that leaves the host. The relative path is recorded because a reviewer needs it; an owner who considers names sensitive can scope the jail so they are not.
- U3. The client prints the same line for its side, so both ends of one copy can be matched by digest and time.
- U4. A refusal reads `refused: <rule> (<detail>)` on the wire, with the same rule id as the audit outcome, so the client's line and the daemon's line match.

## 8. Credentials and the custody boundary (SOUL section 3, ADR-009)

A file channel can move anything, including a credential file. The test is the most durable artifact marvel would hold:
- In transit, the bytes are in marvel's memory for the length of one call. ADR-009's 2026-10-19 amendment permits third-party bearer material in memory while running.
- At rest, marvel writes the bytes only into the owner's jail, a directory the owner named, and keeps only the digest. marvel's own state (its home, its store, its logs) never holds the content.
- So cp is not custody by marvel, but it is a way for a person to move a secret without the credential plane's scoping, and the credential plane is the path for key material (ADR-009). The design does three things about that, none of which is a control a determined caller cannot pass:
  - K1. A fixed refusal list for common credential file names (`auth.json`, `*.pem`, `id_*` without `.pub`, `.env`, `*credentials*`, `*.kdbx`), on whenever the channel is on, checked against every component of the path, in both directions. The owner cannot change it (V7, fixed list, 5-0): a policy key that names it is an unknown key and refuses the call.
  - K2. The help text and the refusal message point to `marvel credential` for key material.
  - K3. No content inspection. Scanning bytes for secrets would put marvel in the business of reading them, which the boundary argues against. This is a review item for the build, not a test row.

## 9a. A scheduled publish verb, and the bound on its reads

**Why this is written here.** The jail in section 3 and the policy in section 6 limit what cp itself can read and write. A scheduled publish verb, run by the daemon with no one at the keyboard, would read files on its own. If its reach were left to its own configuration, it could be built to read anything that configuration names, and the containment cp was ruled on would not hold for it. This section records the ruling and its bound so a later build has to meet them.

**The ruling.** Desk card fileshare-3, 2026-11-02: option 3, "marvel verb, run by the daemon on a schedule." The card named its cost as "as option 2, and it publishes with no owner at the keyboard". Option 2's cost was that marvel gains read reach outside the cp jail. The operator confirmed the bound below on 2026-11-02.

- P1. The owner's policy file, the one marvel cannot write, gains a per-workspace entry naming the verb's read paths, separate from the jail and its prefixes (A3) and under the same A1 checks. The paths are named there and nowhere else. The scheduled verb reads only those paths; nothing outside them is read or packed.
- P2. A missing, unreadable or daemon-writable policy file turns the verb off, by the same checks and with the same refusal that A1 and A2 apply to cp. There is no built-in default list of paths.
- P3. The verb is generic. It takes the paths the owner lists, as `<owner-listed path>` entries, and knows nothing of the layout of any other component. No path belonging to another component is built into it (ADR-005, component independence).
- P4. The policy is read on each scheduled run, before anything else, as A1 reads it for each cp call. Removing the file or setting `enabled = false` (A6) stops the next run. This follows from P2 and A6.

**Not decided here.** Which paths the owner lists is the owner's to name, not this section's. The publish set and any one-way mirror are separate items, recorded elsewhere; a mirror needs its own design note. This section names no real directory and sets no publish set.

## 10. Out of scope

Directories, recursion, streaming, resumable transfer, files over the transport limits (I3), seat-to-seat copies on one host that need no daemon, any write to a company root or installer store, distributing casts or company versions, any content inspection, and any change to how `marvel work` resolves a workspace root. Also out of this build: a bounded drain of in-flight cp calls on shutdown (the intent line makes the gap visible, and a drain changes shutdown for every method); `os.Root` behaviour across a bind mount inside the jail on Linux, which was not checked (C4 leaves mounts to the owner).
